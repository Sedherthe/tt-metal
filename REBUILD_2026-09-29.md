## What to rebuild, in order

### R1. #36487: ROW_MAJOR-prepared weights as a safety-check candidate

Finding (09-28): `ttnn.prepare_conv_weights` with `input_layout=TILE_LAYOUT` (what we pass, matching the activation) produces wrong weights whenever conv1d internally decides to DRAM-slice, because the op then reads ROW_MAJOR internally. Declaring ROW_MAJOR fixes those geometries but breaks ones TILE gets right. No single layout is correct everywhere.

Measured relative error vs a float64 conv (standalone):

| Geometry | Declared TILE | Declared ROW_MAJOR | Raw weight |
| --- | --- | --- | --- |
| HiFT resblock k=11, d=1/3/5 (5,120) | 1.40-1.51 | 0.0039-0.0041 | same as ROW_MAJOR |
| source_downs[0] k=30 s=15 (8 lengths) | 1.23 | 0.0039-0.0046 | same |
| source_downs[1] k=6 s=3 (6 lengths) | 1.13-1.15 | 0.0039-0.0057 | same |
| flow decoder conv k=3 (5,120) | 0.0029 | 1.33 | 0.0029 |
| resblock k=11 (10,240), clean | 0.0039 | 1.37 | 0.0039 |
| source_downs[0] (61,441), clean | 0.0018 | 1.3e36 | 0.0018 |

#36487's own reproducer: PCC 0.225 (TILE) -> 0.999912 (ROW_MAJOR).

Build: add the ROW_MAJOR-prepared weight as a fourth candidate in the conv safety checks, tried before the raw weight. Convs stay on prepared weights wherever correct; checks remain the guard. The flow conv at the 2,560-token bucket (Conv1d 320->256, k=3, length 5,120) is wrong both ways (2.13 / 2.27) and stays on raw (0.0026). Add a unit test on a real broken geometry, nothing simulated (TILE gives inf, ROW_MAJOR 0.0039, same as raw).

Rejected and recorded in FINDINGS: converting conv inputs themselves to ROW_MAJOR broke 30 other convs and made HiFT 22-28% slower, though HiFT PCC vs torch improved 0.9909 -> 0.9966 (a possible future accuracy lever).

Expected effect: no Stage 1 output change (the two HiFT geometries we run were already clean); a partial recompile (~898 kernels).

### R3. Streaming stage A: offline streaming from fixed tokens (no LLM, no trace)

Streaming flow + chunked HiFT over upstream's hop schedule (25 -> 50 -> 100 tokens), driven by precomputed tokens. Design points found on 09-28:

- **Upstream's final chunk runs the flow non-streaming.** The last `token2wav` call in `tts()` doesn't pass `stream`, so it defaults to False (full attention over all tokens). Ours must match: the final chunk uses the existing bucketed non-streaming flow (already warmed) and takes only the new frames. The earlier "streaming final chunk" path does not match upstream; record that in FINDINGS.
- **The streaming encoder must not create a new conv geometry per chunk.** Place the 3 lookahead tokens right after the valid rows so everything runs at the bucket length; earlier rows then see exactly what upstream computes, and the geometry set stays finite (warmable before the decode trace).
- **HiFT chunk sizes:** middle chunks 108 and 208 frames at exact size; the first chunk (50-98 frames) and the final chunk are padded with silence to 128 or 256. **The first chunk must be padded in front**, otherwise HiFT's look-ahead corrupts the first crossfade.
- Check the emitted audio of padded chunks against upstream, not only the seams: silence padding reached back 0.22-0.38 s in the earlier bucketing test, more than the ~8-frame held-back region.

Gate, against upstream's own streaming run on the same tokens (reference venv): per-chunk mel comparison, with upstream's non-streaming mel as a control that must differ; HiFT fed upstream's mels with injected F0 and the same noise, checked at each seam; spectral metrics with our own F0; WER/SIM on the six streamed utterances.

Previously measured: mel per chunk 0.0085-0.018 relative error; vocoder seams PCC >= 0.999; WER/SIM 0.68% / 95.81 vs upstream's 0.68% / 95.89.

### R4. Streaming stage B: interleaved with the LLM

- `generate(on_token=...)` drives a `StreamSession`; hop resets to 25 per utterance (upstream carries it across requests at model.py:360; we deliberately don't).
- Trace schedule: every streaming geometry is compiled and verified before the LLM decode trace is captured, so no safety check runs while it's alive; the trace is released before the final chunk; nothing left alive after a call.
- HiFT streaming state parked on the host between chunks (~30 KB).
- Tests: at least one chunk emitted during generation; greedy streamed tokens equal batch tokens; no trace left alive.
- The new 108-frame HiFT length hit #36487 on six convs; the R1 ROW_MAJOR candidate fixed all of them. **R1 must land before B.**

Previously measured: no hang on Wormhole (N150, KMD 2.3.0); streamed audio bit-identical to offline streaming; greedy tokens equal batch.

## Decisions already taken (don't re-open)

- Final chunk: keep upstream parity (non-streaming).
- Flow caching: dropped (prompt is 15-19% of the flow; gain ~0.1 s TTFP; 2.3 MB of device memory per mel frame; breaks final-chunk parity).
- fp32-logit LLM head stays the default.
- Chunked HiFT (512-frame chunks, last chunk anchored to the end) for non-streaming.
- Deterministic warm-up at process start (the kernel-cache address issue).
